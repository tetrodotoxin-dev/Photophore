# Photophore

Photophore is Tetrodotoxin's Vulkan based windowing, input and rendering runtime
built on [Perimortem](https://github.com/tetrodotoxin-dev/Perimortem).
It acts similar to frameworks like GLFW or SDL and wraps the native runtime, but
in a much more limited fashion.

Linux supports Wayland only (no X11 support currently) and Windows. Web isn't
supported at this time.

## Generated graphical programs

Photophore's primary consumers are graphical TTX programs generated by
[Tetrodotoxin](https://github.com/tetrodotoxin-dev/Tetrodotoxin), and their
requirements define its direction. Independent applications can use the same
runtime, but its evolution follows the generated-program boundary.

Tetrodotoxin code generation defines the work performed on both sides of the
CPU and GPU boundary, including the data that crosses it. It publishes the host
layout and resource description together with the matching embedded SPIR-V
modules, keeping one generated contract as the source for both sides.

Generated programs extend Photophore by publishing a description at its
pipeline boundary. Each description supplies the stages, resources, vertex
inputs and host inputs required to construct its Vulkan pipeline. Photophore
validates that contract, realizes the native pipeline and reuses its device
resources across frames. Consumers can add graphical programs without adding
corresponding pipeline implementations to Photophore.

Frame batches select a generated program by identity and provide the values
that change for one draw: images, parameters, placement, size and ordering.
Pixel content remains separate from its sampling policy, allowing several
generated programs or draws to reuse one uploaded image without sharing their
filtering and addressing choices.

## Window and execution model

Windowing supplies the native rendering surface Vulkan needs and a configurable
input surface for generated programs. Input mappings translate physical
controls into the program's vocabulary, while event status, logical dimensions
and scale expose the host observations needed to respond to that surface.
Together with Perimortem's system capabilities this keeps operating system
integration behind one runtime boundary.

Applications own the frame loop, rendering system and update schedule. They
decide when to poll input, respond to resize events, begin a frame, order and
record draw commands, and submit that frame for presentation. Photophore
supplies the native surface, resource realization and synchronization needed to
carry out those decisions.

Synchronization favors correctness across different generated programs and
frame schedules over optimization for one known workload. That policy may be
suboptimal for high performance systems such as game engines. Those systems can
still use the model, but should measure and specialize the synchronization
policies their workload requires.

The [demo](examples/demo.cpp) exercises that complete path with authored shader
programs, image content, input mapping, resize handling and ordered draws. Run
it from the repository root with:

```sh
bazel run :demo
```

## Building and testing

Python 3 and Bazel are required. The Bazel version is specified in
[.bazelversion](.bazelversion), and [MODULE.bazel](MODULE.bazel) declares the
Toolchain and Perimortem dependencies used to build the project.

Run these commands from the repository root:

```sh
bazel run :format -- --check
bazel build //source/...
bazel run :tests
bazel run :benchmarks --config=release
bazel build :sdk --config=release
bazel run :snapshot
```

Tests and benchmarks are standalone executables. The SDK packages component
headers and static and shared libraries for independently built consumers. A
snapshot archives the clean Git commit that reproduces the source and
validation state.

Run the same portable tests as a standalone WebAssembly program with:

```sh
bazel run :tests --config=web
```

The native presentation check requires a working presentation environment and
graphics driver:

```sh
bazel test :presentation
```

For VS Code tasks, debugging and header navigation, run `bazel run :vscode`.
